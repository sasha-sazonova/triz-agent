# Метод LITE — базовый маршрут (8 шагов)

> Режим по умолчанию. Артефакты пишутся в `projects/<задача>/`. Каждый шаг = файл.
> Формулировки артефактов — на языке задачи; номера/имена параметров и принципов
> дублируются EN из `knowledge/`.

## Этап 0 — Приём задачи → `01_task.md`
1. Перескажи задачу одной фразой: техническая система (ТС) + функция + проблема
2. Мини-задача: «Всё остаётся как есть, но [вредный фактор] исчезает»
3. Определи: компоненты ТС, надсистема, условия эксплуатации, ограничения
4. Если данных не хватает — максимум 2 уточняющих вопроса; дальше — допущения с пометкой `[допущение]`
5. **Гейт:** пользователь подтвердил мини-задачу

## Этап 1 — Противоречие → `02_contradiction.md`
Субагент CONTRADICTION_MINER (`craft/CONTRADICTION_MINER_AGENT.md`) или сам, если задача простая:
1. Техническое противоречие (ТП): «Если [A], то [полезно X], но [вредно Y]» — для обеих веток
2. Маппинг на параметры: improving ∈ 39, worsening ∈ 39 (проверь имена по `knowledge/39_parameters.yaml`)
3. Административная формулировка («сделать X» — что просили) vs техническая (в чём конфликт)
4. В конец файла добавь строку-маркер для автопроверки:
   `<!-- eval: pair=<improving>,<worsening>; approx=<true|false> -->`
5. **Гейт:** пользователь подтвердил противоречие (или оно очевидно из задачи)

## Этап 2 — ИКР и ФП → `03_ikr.md`
1. ИКР-1: «[Элемент] САМ выполняет [функцию], не вызывая [вредный фактор], без усложнения системы»
2. Физическое противоречие (ФП) на ключевом элементе: «должен быть [P], чтобы X, и не должен
   быть [P], чтобы Y» (например: «труба должна быть широкой для пропускной способности и
   узкой для прочности»)
3. Усиление: к какому элементу/зоне/времени привязано ФП (оперативные зона и время)

## Этап 3 — Принципы и эффекты → `04_principles.md`
1. Матрица: `python3 scripts/matrix_lookup.py <improving> <worsening>` → 3-5 принципов
2. Для каждого: одна строка — как принцип разворачивается в ЭТОЙ системе (не абстрактно!)
3. Если строка не пишется — принцип нерелевантен, так и запиши
4. Эффекты: субагент EFFECTS_LOOKUP — какие физические/химические/геометрические эффекты
   реализуют нужную функцию (`knowledge/effects_database.json`)
5. Тренд: есть ли у системы явный шаг по законам эволюции (динамизация, переход в надсистему…)
6. В конец файла — маркер: `<!-- eval: principles=<№,№,№ в порядке ранга> -->`

## Этап 4 — Концепции → `05_concepts.md`
1. ≥3 концепций из разных классов (разные принципы/эффекты — не вариации одной)
2. Каждая: суть (2-4 предложения) → трассировка (`Принцип N (Name) / эффект Z`) →
   что улучшает → что может ухудшить → грубая осуществимость
3. Однотипность — тупик другого рода: если концепции ложатся в <3 РАЗНЫХ классов
   (по принципам/эффектам) или критик в прошлых раундах пометил `MONOCLASS` —
   вызови субагента SYNECTIC (4 типа аналогий) для новых КЛАССОВ решений,
   а не вариаций имеющихся

## Этап 5 — Критика → `06_critique.md`
1. Субагент CRITIC: scorecard по каждой концепции (физичность / новизна / реализуемость /
   стоимость-сложность / близость к ИКР), вердикт PASS / CONSIDER / FAIL — см. файл критика
2. Если критик пометил `MONOCLASS` → вернись на Этап 4 через SYNECTIC (один раунд)
3. Патентная проверка концепций уровня PASS/CONSIDER: субагент PATENT_CHECKER (researcher + API)
4. Итог таблицей: концепция | вердикт | почему | что доработать
5. Если после двух раундов нет PASS/CONSIDER → **триггер DEEP** (см. AGENTS.md)

## Этап 6 — Синтез и отчёт → `07_report.md`
1. Собери отчёт по шаблону `methods/REPORT_TEMPLATE.md`
2. Если несколько выживших концепций — сводиная таблица + рекомендация (одна ставка + запасная)
3. **Гейт:** пользователь утвердил отчёт → задача в `archive/`, уроки — в `.learnings/TRIZ_LEARNINGS.md`

## Правила режима
- Один этап — одна сессия работы максимум; между этапами артефакты на диске (gate control)
- Оценка времени: LITE без ресёрча ≈ 5-10 мин; с патентной проверкой ≈ 15-40 мин
  (researcher асинхронный, cron-забор +20 мин)
